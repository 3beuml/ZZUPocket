## 二、信息架构

### 2.1 底部导航：4 个 tab

```
┌──────────┬──────────┬──────────┬──────────┐
│   今天    │   课表    │   专注    │   校园    │
└──────────┴──────────┴──────────┴──────────┘
```

设计原则：**打开 App 3 秒内要知道"现在该干什么"**。所以第一个 tab 是聚合页，不是课表。

### 2.2 「今天」——聚合首页

按优先级从上到下：

| 区块 | 内容 | 依赖 |
|---|---|---|
| **① 现在在干什么** | 由课表时间轴推导：<br>上课中 → "正在上《高等数学》· 距下课 23 分钟"<br>课间 → "课间休息 · 还有 7 分钟上课"<br>空档 → "下一节 14:00《大学物理》· 1 小时 20 分后" | 课表（本地计算） |
| **② 番茄钟快捷入口** | 一键开始 / 今日累计专注 + 今日标签分布 | 纯本地 |
| **③ 今日课表时间轴** | 纵向时间轴，已过/进行中/未开始三态 | 本地 |
| **④ 近 12 周热力图小卡** | 点开进「专注」tab | 纯本地 |
| **⑤ 状态卡** | 剩余电量 + 校园卡余额（各带"数据截至") | 打开时刷新 |

**未登录时**：①③⑤ 位置显示一张引导卡"登录后查看课表 / 电量 / 校园卡"，②④ 照常可用。

### 2.3 「课表」

- 主视图：**7×10 周网格**，顶部显示"第 N 教学周"，左右滑动切周（用 `HorizontalPager`）
- 点课程 → 底部弹出详情（教师 / 地点 / 周次 / 关联标签），用 `ModalBottomSheet`
- 顶部可切学期
- **星期表头下面带日期**（`10-01` 这种完整月-日，每列都有；今天那一列用主色加粗），
  日期由 `ScheduleText.mondayOf(学期起始日, 第 N 周)` 算出来 —— 算不出（没选学期/没同步）就不显示日期。
  周次标题下面那行「9/21 - 9/27」的区间**已按用户要求删掉**："这是哪几天"改由表头日期回答。
- **表头固定**：往下翻课表时"周几 + 日期"一直看得见（表头在可滚动区之外；
  它只是一行普通 `Row`，不吃横向拖动，所以左右翻周的手感不受影响）。

> 📌 **变更（用户确认）**：**空教室已移到「校园」tab**。本 tab 只保留课表本身，不再做课表/空教室的 Segmented 切换。

#### ⚠️ 周次翻页器的两个坑（都在真机上踩过：课表页停在上一周）

现象：今天页写着「第 4 周」，课表页却停在「第 3 周 / 9/21 - 9/27」，点一次刷新才对。

1. **翻页器与 ViewModel 不能互相驱动**。曾经的写法是
   A「`currentPage` 变 → `goToWeek(那一周)`」+ B「`weekIndex` 变 → `animateScrollToPage`」，
   于是：`weekIndex` 默认 1 → 翻页器以第 1 周挂载 → 真实周次（第 4 周）到达后 B 开始
   从第 1 周滚过去，**动画每经过一页 A 就把那一周写回 ViewModel**，而 `weekIndex` 一变
   B 的协程被取消 → 动画停在中间页 → A 再写一次 → 稳定卡在**过去的某一周**
   （起始页永远是第 1 周，所以只会往过去卡，正好对上用户说的"显示之前的课"）。
   修法：A 只听 `settledPage` 且 `!isScrollInProgress`（程序化滚动期间一律不回写）；
   B 保留单向"VM → 滚过去"。
2. **周次没解析出来之前不要挂翻页器**。`bootstrap()` 先给 `weeks`（19 周）、后给真实
   `weekIndex`，中间那一小段默认值 1 就是上面那条的起点；用 `weekResolvedOn` 判断，
   解析完再挂，初始页直接是本周。
3. **跨天要重算**：`weekIndex` 只在首次载入/手动刷新/换学期时算过，`onResume` 什么也不做，
   所以隔天（尤其跨周）打开还停在旧周。现在用 `WeekAlignment`（纯函数 + 单测）：
   **同一天内**用户手动翻的周保留，**隔天**自动回到当前周。

### 2.6 桌面小组件（RemoteViews + XML，已实现）

用户黏性最高的一块。当前三个（代码都在 `app/src/main/java/com/zzupocket/app/ui/widget/`）：

1. **下一节课** — 2×2：**一节课大字 + 右上角圆气泡 + 一行预告** ——
   表头「今天 · 第 N 周」，下面是课名（20dp 粗）/ 完整时间段 / 地点，底部一行「→ 14:00 程序设计基础」，
   圆气泡是"这节课以及之后还有几节（含本节）"。今天没了但明天有 → 顶上明天的第一节（表头「明日预告 · 第 N 周」）；
   今明都没课 → 一句「无课程」。
2. **今明课表** — 4×2，照拾光的「近日课程4x2」：右上角「第 N 周」，左列「今天 9.29 周二 ＋ 剩余 N 节」，
   右列「明天 9.30 周三 ＋ 共有 N 节」，每列两行课程块，某列没课就居中「无课程」。
3. **电量与校园卡** — 4×2，**左右两半、每半两个数据块**（左：照明/空调 ＋ 可用约 N 天；
   右：余额/本周 ＋ 今日消费/笔数），右上角更新时间；**两块分区可点**：左半 → 电费页、右半 → 校园卡页。

> ⚠️ **2×2 别再改回"一行一节的列表"**。中间那版那么做过（照拾光的 `CompactNativeRenderer`：
   表头「周二 ＋ 剩余 N 节 ＋ 第 N 周」+ 多行课程块），真机上被否掉：
   ① 今天上完、明天又没课时，整个内容区只剩一句状态，**看着像组件坏了**（用户原话"左边没有东西"）；
   ② 列表版把 4×2 的「明天的课看右边」文案带进了 2×2 —— **2×2 根本没有右边**。
   现在的形态是用户认可的：一节课占大块，一眼就知道下一节是什么、几点、在哪。

**一块课程 = 左侧课程色条 + 课名（15dp 粗）+ 一行「地点（左）／时间段（右）」12dp**，
**不显示老师**（用户要求）。4×2 的两列共用同一套行布局 `widget_course_row.xml`，观感才一致
（2×2 只有一节课，直接写在 `widget_next_class.xml` 里）。

**判断逻辑**：「还没下课」= `end_time > now`（正在上的算在内，左闭右开）；
4×2 左列只列今天还没下课的、右列列明天全部；
**"没课"的文案只有一句「无课程」**（4×2 的空列、2×2 的今天没课/今天上完了，都是它）——
以前分成「今天没有课程」「今日课程已结束」两句，用户要求统一。
只有两种情况**不写「无课程」**，因为写它会误导：
**假期**（→「假期中 / 期待新学期」）和**还没同步过课表**（→「还没有课表数据 / 打开 App 同步课表后显示」），
两者都整块盖住内容（4×2 的两列也不画）。

### ⚠️ 尺寸：声明值、options 值、真实画布是三回事（这轮踩得最惨）

| 来源 | 4×2 | 2×2 |
|---|---|---|
| provider 声明（官方老公式 `70n−30`） | 250×110dp | 110×110dp |
| `AppWidgetManager` 的 options | 342×195dp | 163×195dp |
| **真实画布（view tree 量出来的根容器）** | **342×165dp** | **163×165dp** |
| 桌面格子的实际尺寸 | 每格 89.5×105.8dp | 同 |

- 声明按官方公式写 → **启动器只给 3 列**（它按自己的格子算：3 列 = 247dp）。要 4 列得声明 ≥340dp
  （所以现在声明 340×165dp），而且**不能关掉横向拉伸**（关了就自己也没法拉宽）。
- options 报的高度**比真实画布多 30dp**（启动器自己的内缩）→ 按 options 排的版面会"上挤下空"，
  所以 `Widgets.sizeDp()` 里统一减掉 30dp 再用。
- 布局里**不要用 `layout_weight` 去撑满**：实测在 RemoteViews 这层嵌套里不生效
  （列容器不会撑满，最后的差额全由最后一个孩子吸收 → 末行文字被裁）。
- **`setInt(id, "setMinimumHeight", px)` 也没用**：它是反射调用，而 Android 只放行带
  `@RemotableViewMethod` 注解的方法（`View.setMinimumHeight` 没有）。同理 `setBackgroundTintList`
  **有**注解，所以着色一直正常。要"撑高"就用 API 31 的 `RemoteViews.setViewPadding`（正经 API），
  并且**只温和地撑、留出余量**，否则末行会被裁（见 `Widgets.stretch` / `WidgetSchedule.courseRowHeightDp`）。

### 点击跳转（点电量去电费页、点余额去校园卡页）的四个坑

1. **PendingIntent 的 requestCode 必须按目标分开**：Android 判两个 PendingIntent 是不是同一个，
   只看组件/action/data/category，**不看 extras** —— 用同一个 requestCode，后建的 extras 会覆盖
   先建的，表现就是"点哪个都跳同一页"；
2. 路由字符串抽到 `ui/nav/AppRoutes.kt`，AppNav 与组件共用一份，避免改名时静默失效；
3. MainActivity 读到路由 extra 后**立刻 `removeExtra`**：不删的话转屏/切深色模式会再跳一次；
4. 目标页**不是** NavHost 的 startDestination，而是**先落到今天页再把目标页压上去**，
   否则返回键会直接退出 App（和从「更多 → 电费」点进去的手感也不一致）。
5. **目标若是底部 tab，必须走 `switchTab()`**，不能用裸 `navigate()`。tab 切换带
   `popUpTo(起始页){saveState=true} + restoreState=true` 的记账，裸 navigate 压栈会让
   "今天"那一格保存的回退栈里夹着别的 tab；之后每次点「今天」都被 `restoreState`
   恢复成那个 tab —— 表现就是"从组件进来以后点今天没反应"（真机复现：
   课表页点今天仍在课表页、从专注页点今天又被弹回课表页；对照组正常路径完全没问题）。
6. **同一个路由连点两次也要能再跳**：`LaunchedEffect` 只拿路由字符串当 key 时值没变、
   不会重跑，所以 MainActivity 额外传一个自增的 `routeToken` 当 key；
   同时补上 `onNewIntent`（组件 Intent 带 CLEAR_TOP，App 已运行时系统会重建 Activity
   并走 onNewIntent，只处理 onCreate 会把这条路径静默丢掉）。

**技术路线：AppWidgetProvider + RemoteViews + XML 布局，不用 Jetpack Glance。**

这条是**试错后的结论**，不是一开始的选择。最早三个组件是 Glance 写的，实践中撞了三堵墙：

| 问题 | Glance | RemoteViews（现状） |
|---|---|---|
| 「添加小组件」的选择页看不到预览 | 1.1.1 **没有** `providePreview`，只能给一张固定图（旧版实际给的是 **App 图标**，等于没有预览） | `previewLayout` 让启动器**直接渲染真实布局**（改布局预览自动跟着变） |
| 行数随盒子高度变的课表列表 | 响应式 `SizeMode` 只切几档预置布局，行数写不死 | `RemoteViews.addView` 动态加行，按盒子高度算能放几行 |
| 视觉细节（3dp 色条、行距、字重） | 要迁就 Glance 的修饰符子集 | 就是普通 XML，量得准、改得动 |
| 分区点击（同一组件内不同区域去不同页） | 只能说"整块一个 action" | `setOnClickPendingIntent` 可以挂在任意带 id 的视图上 |

另外几条从上一版沿用/总结出来的硬口径：

- **组件里不打任何网络请求**，只读本地数据。桌面是系统在后台唤醒我们去画的，
  在那里发请求等于让用户莫名耗电、网络一慢组件就白屏。拉数据交给 App 打开时和已有的定时任务。
  **校园卡余额只能联网查**，所以由 App 查到后存进 `CardBalanceStore`，组件只读这份缓存 ——
  代价是可能不新，因此组件右上角会如实标注更新时刻（`21:03 更新` / `昨天 20:03` / `3 天前`，
  取三份数据里**最旧**的那份，宁可保守）。
- **不做实时倒计时**。系统对组件的定时刷新下限是 30 分钟，长时间挂着一个错的倒计时比不显示更糟。
  只显示上课**时刻**；补偿手段是在下一个上下课时间点定一个（非精确）闹钟，
  让组件正好在该变的时候变一次（见 `Widgets.scheduleNextBoundary`）。
- **电量/余额的数字独占一行、右对齐**。上一版把数字和表计名放同一行，
  余额一到 `1288.5` 就被截断（半宽 110dp 放不下 114dp 的内容）。
  状态用颜色 + 留白处的小字表达（「已欠费」「可用约 0 天」），不去抢数字的宽度。
- **推算值一律写「约」**：用量趋势是本机每 4 小时采样推出来的（学校不给历史用电量，
  WorkManager 还会被系统压制），所以「可用约 32 天」而不是「可用 32 天」；
  没有样本就说「暂无用量样本」，流水没同步就说「未同步」，**绝不用 0.00 假装**。
- **「还能用几天」的口径只有一份**：`EnergyStats.DAYS_LEFT_WINDOW_DAYS` +
  `recentDailyAverage()`（**按表计各自**算日均），电费页与组件都引它。
  两处各写一份的后果是真机上同时显示「约 28 天」和「15.9 天」——
  曾经电费页拿"照明+空调合计日均（120 天窗口）"去除每一路的余额，
  而组件按表计各自算近 7 天；用户正拿这个数判断要不要充电费，不能有两个答案。

细节与坑（圆角为什么用系统 dimen、字号为什么用 dp 而不是 sp、颜色怎么刷进 RemoteViews、
预览图怎么生成）都写在 `ui/widget/` 各文件的类注释里。

### 2.7 视觉规范

- **Material 3 动态取色**（Android 12+），低版本回退静态色板（建议用郑大主色调）
- 深色模式跟随系统
- 字体大小档位可调（可参考 GdeiAssistant 的四档）
- 数据新鲜度用**弱化的小字 + 图标**表达，不要弹窗打断

## 三、登录流程设计

### 3.1 登录放在哪：推荐「引导 + 按需」双轨

**核心判断：番茄钟、标签、热力图、总结完全不依赖登录。这是 App 的"无登录核心价值"。**

| 场景 | 建议 |
|---|---|
| **只自己用** | 首启动走一次引导登录，**允许"先跳过，只用番茄钟"**。登录后一劳永逸 |
| **想给同学用** | 必须按需登录。一上来就要学号密码 + 短信码，会立刻流失 |

具体流程：

```
首启动
  ↓
「今天」页（可用，番茄钟正常）
  ├─ 用户点需要数据的功能（课表/电量/校园卡/图书馆）
  │      ↓
  │   全屏登录页 → 登录成功 → 立即"首拉"（课表+余额+电量+预约记录）
  │      ↓
  │   回到刚才那个页面，数据已就绪
  └─ 或 用户点首页引导卡 → 同上
```

**为什么不做成"首启动强制登录"**：除了会流失，还有一个具体副作用——首次登录要发短信验证码，而账密登录还会把手机上的豫见郑大踢下线。把这两件事塞在"第一次打开 App"的体验里，成本太高。放到用户真正需要数据时，他能理解这个代价。

### 3.2 统一登录页（关键设计）

**一次登录解决四套系统**，不要让用户每个功能各登一次：

```
统一身份认证（学号 + 密码）
        ↓
   CAS userToken / refreshToken
        ├─→ 教务 EAS      （自动）
        ├─→ 一卡通 ECard  （自动换 tid → accessToken）
        └─→ 图书馆        （自动）
```

登录页要素：

| 要素 | 说明 |
|---|---|
| 字段 | 学号 + 密码 +（仅首次）短信验证码 |
| **⚠️ 副作用提示** | **必须明确告知**："首次登录会使手机上的豫见郑大下线一次，之后不会。" ——这是 zzupy 文档确认的事实，隐瞒会导致用户以为 App 有问题 |
| **可信设备引导** | 登录成功后弹一张卡片，引导跳转 `authx-service.s.zzu.edu.cn/security-center/eqIP-management` 把本设备设为可信设备 → **之后不再需要短信码** |
| 记住的 | 只记住学号（可选），**绝不记住密码** |
| 错误分类 | 密码错 / 需要 MFA / 网络不可达（提示可能需校园网或 WebVPN）/ 账号异常 —— 分开提示，不要统一报"登录失败" |

### 3.3 登录状态不是一次性 gate，而是一个生命周期

必须有一个「**登录状态与诊断**」页面（借鉴 xjtu 的"登录诊断"）：

- 各系统令牌状态：CAS ✅ / 教务 ✅ / 一卡通 ✅ / 图书馆 ⚠️（3 小时前）
- 各令牌最后刷新时间
- 手动"重新登录"按钮
- 清除本地数据 / 退出登录

**理由：令牌过期是这套 App 最主要的故障来源，而且会静默失败。** 有诊断页，用户（就是你自己）能一眼看出是"接口挂了"还是"登录过期了"。

### 3.4 可选：生物识别锁

本地存了课表、消费记录、电量历史。可加一个"打开 App 需指纹/面容"的开关（默认关）。纯本地校验，不上传任何东西。

## 四、数据：哪些存本地，哪些要定时拉

### 4.1 先纠正一个心智模型：不要把它想成"爬取"

正确的心智是——**四种模式**：

| 模式 | 含义 | 适用 |
|---|---|---|
| **A. 一次性拉取 + 长期本地保存** | 拉一次够用很久 | 课表、学期列表、节次时刻表、教学楼/房间列表 |
| **B. 事件驱动增量同步** | 只在有新增时才有意义 | 校园卡交易、图书馆预约记录 |
| **C. 交互时实时查询** | 变化快，缓存无意义 | 座位占用、余额、剩余电量 |
| **D. 本地推导，永不拉取** | 由已存数据算出 | 空教室、日/月用电、热力图、周月年总结、上课提醒 |

**判断原则**：
1. "这个数能不能由本地已有数据算出来？" → 能，就**不拉**（D 类）
2. 不能 → "它多久真的变一次？" → 按真实频率拉
3. 再问"用户什么时候会看到它？" → **只在会看到的时候拉**

### 4.2 逐项对照表

| 数据 | 模式 | 频率 | 理由 |
|---|---|---|---|
| 登录 token | A（长期保存） | 失效才重登 | **绝不重复账密登录**（会踢掉官方 App） |
| 课表 | A + 手动刷新 | **开学 1 次**，之后按需 | 学期级；调课例外 |
| 学期列表 / 节次时刻表 | A | 极少 | 近似常量 |
| **剩余电量 / 空调费** | C + 低频后台 | **30–60 分钟** | 实测：15 分钟内服务端数据完全没变，1 分钟轮询纯浪费 |
| 校园卡余额 | C | 打开时 | 交易驱动 |
| 交易记录 | B | 每天 1 次 | 事件驱动 |
| 图书馆预约记录 | B | 每天 1–2 次 + 打开时 | 事件驱动 |
| **座位占用** | C | **仅打开页面时** | 秒级变化，缓存无意义；也不后台轮询 |
| 空教室 | D（+ 拉一次教室课表） | 拉 1 次 / 周 | 完全可本地推导 |
| 热力图 / 周月年总结 / 日用电 | **D** | **0 次请求** | 纯本地聚合 |

### 4.3 结论：整个 App 真正需要后台定时的只有 3 件事

**电量（含空调费）、交易记录、预约记录** —— 而且频率是 30 分钟 ~ 1 天。

其余全部是"打开时查"或"本地算"。**这让后台请求量可以做得非常小**，既省电，也避免被识别为爬虫。

### 4.4 一个重要的架构取向

**"打开即刷新"优先于"后台定时"。**

原因：国产 ROM 会杀后台任务，WorkManager 在小米/华为/OPPO/vivo 上并不可靠。所以：

- **前台**：进入页面就静默刷新一次（带节流，比如 5 分钟内不重复）
- **后台**：只保留真正必要的低频任务（电量、交易、预约记录）
- **UI**：始终显示"数据截至 XX:XX"，而不是假装实时

这样即使后台被系统杀掉，用户看到的也只是"数据旧了几小时"，而不是"没有数据"。

## 五、给个人自用的取舍建议

这是"自己用的工具"，不是要发行给学生群体的产品。所以：

1. **不做社区/二手/树洞**（GdeiAssistant 那一半功能直接砍掉）
2. **不做自建后端**（xjtu 的路线，也是合规性最好的路线）
3. **首启动引导登录但可跳过**，别为了"流程完整"牺牲可用性
4. **优先做「今天」页 + 番茄钟 + 热力图**——这三个是每天都会看的
5. **小组件优先级高于任何"更完整的功能"**——小组件决定这个 App 会不会被每天用到
