# 校园助手 Android App — 可行性分析与开发方案

> 目标功能：查课表 / 查空教室 / 图书馆座位预约 / 课表联动番茄钟 / 寝室电费 + 空调电费 / 校园卡余额
> 结论摘要：技术可行性高，**合规与接口可持续性才是真正的瓶颈**。建议按"可控性"而非"重要性"排序开发。

## 一、可行性分级

| 功能 | 典型数据源 | 技术可行性 | 难度 | 风险 |

## 二、前置认知

### 2.1 官方 API 基本不存在

高校教务系统通常不对外提供 API。少数学校信息化中心有 OAuth2 / API 网关，一般只向院系、社团、有指导老师的项目开放。

**行动项**：先向学校信息化建设中心 / 网络中心提一次申请（工单或当面问）。
- 成功 → 项目难度下降一个数量级，全部精力可投入产品。
- 失败 → 走"用户自行登录 + 复用会话"路线（见 2.2 方案 A）。

社区参考实现（技术参照物，同时注意它们都随学校改版周期性失效）：
- 正方教务后端查询系统：https://github.com/drfccv/ZFJW-backend
- 小爱课程表新正方适配：https://github.com/z-my-cn/CUFE-XiaoAi
- Java 模拟登录正方抓课表/成绩/空教室：https://www.e-com-net.com/article/1297288905753698304.htm
- 完美校园电费 H5 接口解析：https://doupoa.site/archives/510/
- 小爱课程表适配思路（WebView 抓取 + JS 解析）：https://github.com/z-my-cn/CUFE-XiaoAi

### 2.2 合规红线（决定架构，不是法律课）

参照：长沙理工大学教务处《关于警惕校外APP非法获取学生教务系统信息的严正声明》
https://www.csust.edu.cn/jwc/info/1101/7727.htm

该声明点名三类行为：**诱导学生交出账号密码、自动化脚本抓取、系统漏洞侵入**，引用《网络安全法》《数据安全法》《个人信息保护法》，并声明已加强监测与追溯。

#### 方案 A（推荐）：内嵌 WebView 用户自行登录
- 用户在校方**自己的页面**完成登录，包括验证码、短信、统一身份认证跳转。
- App 从 `CookieManager` 取回登录态，用 `EncryptedSharedPreferences` 加密保存。
- **App 永不接触密码。**
- 优点：合规性最好（等同用户用浏览器查课表）；天然绕过所有登录加密算法与验证码；改版时不需重写加密逻辑。
- 缺点：会话过期需重新登录；部分系统用 HttpOnly cookie + 服务端绑定设备指纹。

#### 方案 B（不建议作为主方案）：代码内实现加密登录
- 在 App 中实现 RSA/AES + 盐值 + 时间戳的登录加密，代持密码。
- 这正是上述声明点名的行为；改版必挂；验证码过不去。
- 仅在确认校方无异议时作为备用。

#### 绝对不要做
- 电费充值、校园卡转账 / 消费类接口（性质从"查询"变为"资金操作"）。
- 代他人查询、抢座 / 秒杀脚本（参考报道：图书馆座位自动"秒"抢工具，涉不当竞争甚至违法）。
- 把校方数据上传到自己的服务器。**App 直连学校服务器，所有数据本地存储**，避免自己成为数据处理者。

## 三、架构设计

核心是多 Provider，不是一个大 API 客户端。

```
UI (Compose) → ViewModel → Repository → CampusProvider (接口)
                                          ├─ JWGLProvider        (课表 / 空教室)
                                          ├─ CardProvider        (一卡通余额)
                                          ├─ ElectricityProvider (寝室 / 空调电费)
                                          └─ LibraryProvider     (座位预约)
```

设计要点：

1. **统一领域模型**：`Course`、`Classroom`、`ElectricityAccount`、`CardBalance`、`SeatReservation`。
   上层 UI 只依赖这五个模型；换学校只换 Provider 实现，不动 UI。
2. **每个 Provider 独立 OkHttpClient 与 CookieJar**，隔离各系统登录域（教务与一卡通是两套会话，混用必互相污染）。
3. **WebView ↔ OkHttp Cookie 桥接**：登录后 `CookieManager.getCookie(url)` → 灌入 OkHttp CookieJar。
   这是方案 A 的技术核心，也是最需要写单元测试的一段代码。
4. **解析层"宽进"**：字段缺失、层级变动、类型漂移（数字↔字符串）都不能崩。返回 `Result<T>`，不抛异常。
5. **远端配置驱动解析**：把 URL、JSON 字段路径做成一份可远端下发的 JSON 配置。
   **接口改版时改配置即可修复，不必发新版 APK** —— 这类项目能否长期存活的决定性设计。
6. **Mock Provider + 真实响应快照**：把抓到的真实 JSON 存为 fixture，对解析层做快照测试。接口随时会挂，没有 Mock 连 UI 都无法调试。

## 四、技术选型

| 层 | 选型 |
|---|---|
| 语言 / UI | Kotlin + Jetpack Compose (Material 3)，单 Activity 多目的地 |
| 架构 | MVVM + Repository + Provider，Hilt 注入 |
| 网络 | Retrofit + OkHttp + kotlinx.serialization，自定义 CookieJar |
| 存储 | Room（课表缓存与快照）、DataStore + EncryptedSharedPreferences（凭据，必须加密） |
| 后台 | WorkManager（≥15 分钟轮询）、Glance AppWidget（桌面课表 / 倒计时） |
| 番茄钟 | AlarmManager `setExactAndAllowWhileIdle` / `setAlarmClock` + Foreground Service + 常驻通知 |

### 系统版本注意事项
- Android 12+：`SCHEDULE_EXACT_ALARM` 权限
- Android 13+：`POST_NOTIFICATIONS` 运行时权限
- Android 14：前台服务必须声明具体类型
- **国产 ROM（小米 / 华为 / OPPO / vivo）会杀 WorkManager 与后台服务**：必须引导用户加入电池优化白名单；关键提醒（上课、下课、低电费）走 AlarmManager + 前台服务，不能依赖 WorkManager 准时。
- 抓包调试：仅 debug build 开 `networkSecurityConfig` 允许用户证书；**release 必须关闭**，否则 App 本身成为攻击面。

## 五、接口侦察工作流（P0 阶段，决定项目 80% 的可行性）

1. 手机与电脑同网段，使用 Reqable / Charles / mitmproxy。
   - Android 7+ 将 CA 装为系统证书需 root；免 root 方案用 Reqable / HttpCanary 的 VPN 抓包模式（遇证书固定会失败）。
2. 微信小程序：分包反编译（wxappUnpacker / unveilr）拿 JS 中的接口与签名算法，比硬抓包更稳。
3. H5：在混淆的 webpack JS 中搜 `sign`、`encrypt`、`timestamp`、`token`、`/api/`。
4. **产物：《接口清单》**（见附录 A 模板）。
5. **先在 Python / Postman 中把全部功能跑通，再写 Android。**
   在 App 里边调边猜接口会把接口问题与 UI 问题搅在一起，调试成本翻三倍。

## 六、开发排期（单人业余）

| 阶段 | 内容 | 工时 | 交付物 |
|---|---|---|---|
| **P0 侦察** | 抓包、接口清单、确认校方态度、决定方案 A/B | 1 周 | 接口清单 + 风险结论 |
| **P1 骨架** | Compose 工程、Provider 抽象、WebView 登录 + Cookie 桥接、Mock | 1 周 | 可登录 + 拉到假数据 |
| **P2 核心产品** | **课表 + 番茄钟 + 桌面小组件** | 1-2 周 | **已是可用的完整产品** |
| **P3** | 空教室查询 | 1 周 | |
| **P4** | 电费 + 校园卡余额 + 低余额通知 | 1 周 | |
| **P5** | 图书馆座位预约（最难，放最后） | 1-2 周 | 失败亦不影响交付 |

## 七、番茄钟 × 课表联动设计

把课表视为一条时间轴事件流，番茄钟是它的状态机。

- 状态机：`Idle → Focus(25min) → Break(5min) → … → LongBreak(15min)`
- **上课段**：自动进入专注（建议式，不强制锁机）
- **课间 10/15 分钟**：自动进入短休息并提醒走动 / 喝水
- **空档 > 45 分钟**：建议一个完整番茄周期（25+5）
- **桌面小组件**："距离下课 23 分钟" —— 用户黏性最高的功能
- **统计与课程绑定**："高数本周 6 个番茄"
- 静音 / 勿扰联动需 `DND access` 权限；国内自用无碍，上架应用商店则属敏感权限

## 八、稳定性与分发

### 频控
- 所有轮询 ≥15 分钟一次，加随机抖动，失败指数退避。
- **绝不高频轰炸**：校方"技术手段监测"正是靠请求特征识别。

### 降级方案
- 课表拉不到 → 支持手动导入 `.ics`
- 电费拉不到 → 保留手动录入提醒
- 任何模块挂掉都不能让整个 App 不可用

### 分发
- GitHub Releases + 自签 APK。
- 国内应用商店上架需软著 + 备案，且"抓取校方系统数据"的应用极易被下架、可能被校方声明点名 → **小范围自用 / 同学间分发是现实选择**。
- 开源时把学校域名与字段抽到不提交的私有配置文件；README 写明"非官方、仅供个人学习"。
