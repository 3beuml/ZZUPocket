## 一、测绘方法（可复用）

- 主包仅压缩未混淆：`/h5/assets/index.<时间戳>.js`（本次 `index.1780450282721.js`，约 1.0 MB），
  文件名带构建时间戳，**从 index.html 里读当前引用**，不要硬编码文件名。
- `208` 个懒加载 chunk 全部可直接 GET。API 模块是小文件（几百字节），
  页面 chunk 通过 `import{g as U,...}from"./sear-record.js"`把它带进来。
- 汇总方法：`grep -ohE 'url:"[/a-zA-Z0-9_.-]+"' *.js` 聚合全部路由。

## 二、预约记录接口（本次需求的核心）

| 用途 | 方法与路径 | 请求体 | 响应 |
|---|---|---|---|
| 座位预约记录 | `POST /v4/member/seat` | `{type:"1"\|"3"\|"4", page, limit}` | `{code:0, data:{data:[...], total}}` |
| 座位违约记录 | `POST /v4/member/seatRenege` | 同上（`type` 同 tab） | 同上 |
| 空间预约记录（研讨间） | `POST /v4/seminar/books` | `{type:<activeKey>, page, limit}` | 同上 |
| 空间违约记录 | `POST /v4/seminar/reneges` | 同上 | 同上 |
| 待处理预约（座位页用） | `POST /v4/space/my_wait` | `{page, limit}` | 同上 |
| 活动预约记录 | `POST /v4/activity/record` | —（未细查） | — |
| 存书柜预约记录 | `（未细查） /reserve/locker/myList` | —（未细查） | — |

- 座位记录 `type` 的三个 tab 来自配置 `my_menu`：`"1"`=普通座位、`"3"`=研习座位、`"4"`=考研座位。
- 记录已知字段（UI 组件用到）：`nameMerge`、`name`、`spacename`、`status`（`"2"`/`"9"` 归为黄色态，其余红/绿）。
  **完整字段表需要一次真实登录后 dump，现在只有 UI 消费到的子集。**
- 未登录形态：`HTTP 200 + {"code":10001,"message":"您尚未登录","data":[]}`（`/v4/member/seat`、`/v4/member/my` 均实测）。
- 票据兑换接口活体确认：无效票据 → `{"code":1,"message":"操作失败","data":{"third":0,"member":[]}}`。

## 三、会话形态（比 LibProbe 的「cookie 会话」更进一层）

1. SPA 拦截器在**每次请求**上加 `authorization: bearer${token}`，token 取自 sessionStorage
   （登录成功从 `data.member.token` 存入）。—— **接口的主会话是 bearer token，不只是 cookie。**
2. 另有 `PHPSESSID` cookie（`/v4/login/cas` 会 Set-Cookie）。
3. `10001` 是未登录信号的统一形态。
4. **待真机验证**：record 接口是否接受「仅 Authorization 头、无 cookie」；token 的有效期（决定静默续期策略）。

## 四、登录三条路（按依赖从少到多）

### 路 1：自带密密的加密登录（可完全原生实现）

`POST /v4/login/login` body `{aesjson: <AES(JSON(user,password,...))>}`，实现就在主包 `HY()`：

- **算法**：AES-128-CBC + PKCS7，`CryptoJS` 风格。
- **key** = `YYYYMMDD + 反转(YYYYMMDD)`（16 字节。`WY(new Date,41)` 就是 `format("YYYYMMDD")`）。
- **iv**（固定 16 字节）= `ZZWBKJ_ZHIHUAWEI`。
- **已验证**：2026-10-29 用当日 key 成功离线解密了 `GET /v4/index/peizhi` 的响应
  （`login:"4"` CAS 模式、`cas_url:"http://order.lib.zzu.edu.cn/v4/login/cas"`、`web:{seatcancel:0,cancel:0,roomcancel:0}`、
  业务开关 `my_menu` 全表）——密钥推导与实现完全对上。
- 用户名密码 = 统一身份认证账密（规则原文见接口现状核查 §10.6），App 已有明文账密可复用。
- **待验证**：登录**响应**是否也加密（`isCryptoPas` 机制只挂在部分请求上，login 调用本身未见挂）、
  学号+密码是否直接就是统认证账密在真实场景成立（按规则原文应成立，但要真机跑一次闭环）。

### 路 2：经典 CAS 兑票（最贴合既定「不逆向加密」红线）

```
GET http://order.lib.zzu.edu.cn/v4/login/cas
  → 302 https://cas.s.zzu.edu.cn/cas/login?service=http%3A%2F%2Forder.lib.zzu.edu.cn%2Fv4%2Flogin%2Fcas
 classical web CAS 出 ST（ticket）后，H5 路由 #/cas 把 query 参数 cas 原样
POST /v4/login/user {cas: <ST>, open_id?}   // open_id 仅微信绑定场景需要
  → {code:0, data:{member:{token, ...}}}     之后全部接口 bearer 这个 token
```

- 应用现有的 CAS 是 **App-JWT 流程**（`cas.s.zzu.edu.cn/token/*` 的 idToken，见 `CasClient.kt`），
  与经典 web `/cas/login?service=` 的 ST **不是同一种票据**，不能直接把 idToken 塞进 `cas` 字段。
- 经典 web flow 可由 WebView 承担（打开 `cas_url`，用户/预填方式登录一次，
  服务端校验 ST 后回跳 `#/cas?cas=...`，我们在 shouldLoad 时截 URL 取 `cas` 参数），
  也可以后续参照 zzupy 社区的经典 CAS 模拟原生实现（要不要走这条路由设计决定，超出本文范围）。

### 路 3：WebView 当登录器 + CookieManager 取会话（LibProbe 既定方案）

`LibProbe.kt` 注释既有结论。今天的发现（bearer token）只是让路 3 的假设（cookie 即会话）多了一个
待验证项：cookie 里是否有会话凭据、还是必须从 `#/cas` 拿 token。若要走路 3，真机一次就能分辨。

## 五、与「层 1 只读」落地方案的衔接

对齐 `接口现状核查.md` §10.8 的分层，本次新增的可行性证明覆盖层 1 所需全部数据：

- 我的预约记录（座位 + 空间 + 违约）→ §二接口，形状已知。
- 展示→ 番茄打卡热力图组件 `FocusHeatmap`/`Heatmap.kt` 是纯 Compose、吃 `Map<LocalDate, Int>`，
  客户端把记录按预约日期聚合成每日预约数即可复用（分档逻辑 `heatTier` 也能直接映射成"预约次数"档位）。
- 数据层模式照抄电费/一卡通：`OkHttp + kotlinx.serialization + Room 落库 + Repository`，
  并用 `rawCall` 风格留自检钩子。
- 剩余大头是 `/v4/Space/map` 楼层座位图的渲染（层 2 选座 UI），以及 WebView 保留策略
  （混合形态：原生数据 + WebView 只做"去预约"动作）。

## 六、红线与风险（继续有效+新增）

1. **签到/签离闭环依赖物理闸机**，App 无法代签（§10.4）。
2. **违规惩罚**：累计 3 次违规停预约权限 7 天 —— 自动化抢座（层 3）维持禁令。
3. **校外仅 HTTP:80 明文**，token 在传输层明文暴露（校方限制，无法从我们这侧根治）；
   按「首次拿 token、只存 token」原则收窄暴露面，密码不落盘优先。
4. 配置里 `web.cancel=0/seatcancel=0/roomcancel=0` 疑似取消按钮的服务端开关，语义未定，
   做「一键取消」前真机确认。

## 七、真机验证结论（2026-10-31，instrumentation + 用户实登）

第七节的待验证项已在真机（MEIZU 21 Note）全部落地，结论如下：

1. **会话通道：token 通道足够**。`Authorization: bearer<token>` 单独就能打通
   `/v4/member/seat`（code=0）；只带 cookie 反而 10001。**cookie 只是兜底，可不再依赖。**
2. **token 捕获闭环成立**：WebView 打开 H5 登录成功后，App 的探测循环几秒内就把
   sessionStorage 的 token 抓回并落盘（logcat `captured lib session token`）。
3. **会话有效期短（实测约 1–2 天）**：10-29 晚捕获的 token 在 10-31 已 10001。
   产品上必须有"过期 → 引导重登"闭环（记录页已内置：报 ReLoginRequired →
   一键跳图书馆页，WebView 自动登录并重新捕获）。
4. **CAS SSO cookie 同样会过期**：无头 WebView 走 `/v4/login/cas` →
   `cas.s.zzu.edu.cn/cas/login?service=…` → `/cas/s/login`（登录表单页），
   两天前的 TGT 不再免密。真机跳转链与服务器侧逆向一致。
5. **记录字段实物**（座位记录，18 条 / total=18；`limit=100` 整页返回）：

   | 字段 | 实测值示例 | 说明 |
   |---|---|---|
   | `id` / `space` / `booker` | 6306382 / 3827 / 学号 | 条目与空间 id、预约人 |
   | `status` / `status_name` | "4" / "已结束" | 状态码 + 中文态 |
   | `beginTime` / `endTime` | `2026-10-29 13:49:34` / `… 22:30:00` | **完整时间戳** |
   | `start` / `end` / `day` | 13:49 / 15:47 / `10-29` | 预格式化展示字段（day 无年份，**别拿去聚合**） |
   | `signInTime` / `signOutTime` | `2026-10-29 14:01:35` / `15:47` | 签到/签离 |
   | `nameMerge` / `no` / `name` | 主校区图书馆-三楼-三楼西 / 007 | 地点与座位号 |
   | `oksign` / `cancel` / `cancelTime` | 0 / 0 / "" | 签到标志、取消 |
   | `timelist` | 数组[3] | 签到时间线（`{status_name, operateTime}`） |

   ⚠️ **响应里没有 `create_time`** —— 热力图聚合日期由 `LibClient.firstReservationDay`
   落在 `beginTime` 候补上解析（实测解出 2026-10-29，正确）。空间记录用下划线形态
   （`begin_time`/`end_time`）且带 `title`（预约事项）与 `teams[]`。
6. **空响应体语义**：`/v4/space/my_wait` 在没有待处理预约时返回**空体**（连信封都无），
   解析层已按 0 条容错；`seminar/books`、两个 reneges 均实测 code=0（该账号 0 条）。
7. **落地**：`LibClient` + `LibSessionSource` + `LibRecordRepository` +
   `LibRecordsScreen`（热力图复用 `FocusHeatmap`，分档换次数口径 `LibRecordStats.heatTier`），
   入口在图书馆 WebView 页顶栏的"日历"图标。单元测试见 `LibClientTest`/`LibRecordStatsTest`。

## 八、本地缓存：不登录也能看历史记录（2026-11-01，用户需求）

**需求**：会话过期后不该"什么都看不了" —— 预约记录是历史数据、不会变，拉过一次就该一直在。

**设计**（`LibRecordRepository`）：

- 缓存落在**现成的 `kv_cache` 表**（key `lib_records_snapshot_v1`，payload 为 JSON），
  **免 Room 迁移** —— 历史 JSON 快照没有"过期"语义，`ttlSeconds=0` 永存，整份覆盖写入。
- `fetchAll()` 成功后写缓存；`fetchAllWithCache()` 现拉失败时回退缓存并带出失败原因
  （`Triple<Snapshot, Boolean, Throwable?>`），UI 据此区分"会话过期"与"网络不通"。
- UI 策略（`LibRecordsScreen`）：
  - 有缓存 + 现拉失败 → **照常显示记录 + 顶部横幅**"显示的是 X 时间拉取的记录" + 更新入口；
  - 无缓存 + 会话失效 → 整页"去图书馆页重新登录"指引（登录后回来自动拉取并存缓存）。
- **真机实证（2026-11-01）**：10-31 23:33 捕获的 token 在 11-01 13:25 已 10001（**有效期
  实测不足 14 小时**，比"1–2 天"更短）；同日缓存兜底正常 —— 会话过期后记录页照常显示
  8–11 月的历史记录（热力图 + 列表 + 横幅），无崩溃。
- 前端版本升级注意：payload 结构变了会解析失败 → `cachedSnapshot()` 返回 null，
  表现为"重新登录拉一次"，无害。
