## 一、总体结论

**接口可以用，但你现在这个项目跑不起来——原因不是接口坏了，是环境配错了。**

三句话总结：

1. **zzupy 在活跃维护**，最新 v7.2.3（2026-08-10 发布），学校改版有作者在跟。
2. **所有后端域名当前全部可达，且不需要校园网**（实测延迟 22–224ms）。教务的三个在用接口返回 401（需鉴权）——注意 401 本身不能证明路径存在，见 2.1 勘误。
3. **你本地环境装的是 zzupy 5.1.0，而你的代码是按 7.x API 写的** → 现在直接 `ImportError`。这是唯一的"不能用"原因，且完全可修。

## 三、环境问题（当前"不能用"的真正原因）

| 项 | 现状 | 要求 |
|---|---|---|
| `import` 语句 | `from zzupy.app import CASClient, ECardClient` | 7.x API |
| requirements.txt | `zzupy>=7.0.0` | 7.x |
| **本机已装 zzupy** | **5.1.0** | ❌ 不匹配 |
| **本机默认 Python** | **3.10.11** | ❌ zzupy 7.x 要求 **≥3.11** |
| 本机可用 Python | 3.14（`py -0p` 标记为默认）、3.10 | ✅ 用 3.14 |

zzupy 5.1.0 的顶层导出是 `ZZUPy` / `api` / `ecard` / `supwisdom`，**没有 `zzupy.app`**，也没有 `CASClient` / `ECardClient`。所以：

```
现在直接运行 app.py → ImportError: cannot import name 'CASClient' from 'zzupy.app'
```

**注意 zzupy 5.x → 6.x → 7.x 是破坏性重构**：老的 `SupwisdomClient` 在 7.x 里变成了 `zzupy.app.eas.UndergradEASClient`（库里有专门的 migration 文档）。你 7 月写代码时用的显然是 7.x 环境，那个环境现在不见了。

**修复方向**：用 Python 3.14 建虚拟环境，装 `zzupy==7.2.3`。

### 4.1 空教室的关键提示

参考河南大学同学写的[空教室查询 API 文档](https://github.com/jry21223/HENU_Assistant/blob/main/docs/henu_empty_classroom_api_doc.md)，有一个很重要的经验：

> 上游系统返回的是"**教室课表**"，不是直接返回"空教室"。需要先拉取教室课表，再根据目标周次、星期、节次**反向计算**空闲教室。

所以空教室大概率不是"一个接口搞定"，而是：拉教室课表 → 减去已排课 → 得到空闲。**这是有真实工作量的模块**（数据量大、要缓存、要按教学楼/节次聚合）。郑大 EAMS 网页版有"空闲教室查询"入口，需要抓一次 XHR 确认是哪种形态。

### 4.2 空调电费的两种可能

- 若空调电费也在 `ecard.v.zzu.edu.cn` 的 utility 体系里（只是另一个 `utilityType` / `payCode`），**改造成本极低**。
- 若是第三方空调租赁平台（独立 App 或小程序），则要单独做一套。

**需要你确认。**

## 五、必须现在就知道的运维细节（这些直接决定架构）

### 5.1 ⚠️ 账密登录会把手机上的"豫见郑大"踢下线

zzupy 作者在逆向笔记里写得很明确：

> 为什么使用 ZZU.Py 进行账密登录，手机上就会被踢下线呢？关键在于 `https://cas.s.zzu.edu.cn/token/login/userOnlineDetect`。豫见郑大 APP 端启动时会通过这个接口上报学号、`deviceId` 和 `userToken`，并根据响应决定要不要让你重新登录。

**对 App 设计的直接含义**：

- ❌ **绝对不要在后台轮询里重复账密登录** —— 否则用户会发现"装了你的 App，官方 App 一直掉线"，这是最容易被卸载的体验问题。
- ✅ 首次登录（账密 + 短信 MFA）拿到 `userToken` / `refreshToken` 后，**只持久化并复用这两个 token**（对应 `cas.set_token()`）。
- ✅ 这样还能顺带做到**完全不存储密码** —— 比 WebView 方案更干净，合规性也更好。

### 5.2 MFA 由 deviceId 决定

- 是否为可信设备决定要不要发短信验证码。
- zzupy ≥7.1.0 内置了固定字符串 `ZZU.Py` 作为 deviceId。
- ⚠️ **你的 Android App 必须用自己独立的 deviceId**（比如包名），**不要沿用 `ZZU.Py`** —— 否则你的 App 会和所有跑 zzupy 的人共用同一个"可信设备"标识，既不安全也混乱。
- 首次登录流程：走一次短信 MFA → 引导用户去 `https://authx-service.s.zzu.edu.cn/security-center/eqIP-management` 把该 deviceId 设为可信设备 → 之后基本不会再要验证码。

### 5.3 其他

- **树维的 `sign` 请求头根本不校验**（作者实测，缺了也行）。这意味着课表接口不需要实现签名算法——**难度大降**，但别把"不校验"当永久前提。
- **一卡通有独立的 `accessToken`/`refreshToken`，45 分钟自动刷新**。App 要按这个节奏维护会话，别每次查询都重新登录 CAS。
- **电费充值用国密 SM2/SM4 加密**（SM4 密钥硬编码 `773638372d392b33435f48266a655f35`，SM2 用 C1C3C2 模式、去掉 `04` 头）。
  → **明确建议：不做充值。** 一是碰钱性质变了，二是在 App 里存支付密码是严重的自我担责。

## 六、技术路线的修正

⚠️ **我第一版方案里推荐的"内嵌 WebView + 复用 cookie"在郑大这个场景下不是最优解**，原因：

- zzupy 已经把 App 端 JWT 认证 + MFA 流程逆向干净了；
- 一卡通要换两次 token，走 WebView 反而是绕远路；
- 郑大接口全都是 `Authorization: userToken` + cookie `userToken` 的**纯 JSON API**，不需要浏览器环境。

### 修正后的方案

**原生 HTTP 客户端 + 在 Kotlin 里复刻 zzupy 的令牌流程。**

接口数量其实很少：

| 模块 | 域名 | 接口数 |
|---|---|---|
| 教务 EAS | `jwxt.zzu.edu.cn/eams-door/...`、`/eams-micro-server/...` | 5 个 URL |
| 一卡通 | `ecard.v.zzu.edu.cn/server/...` + `info.s.zzu.edu.cn/portal-api/...` | 7 个 URL |
| CAS | `cas.s.zzu.edu.cn` | 登录 + MFA + 上报去重 |

**一天量级的工作，不是一周。** 换来原生体验 + 可控后台 + 无第三方依赖风险。

### 要不要在 Android 里跑 Python？

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| A. Chaquopy 跑 zzupy | 零翻译成本，改版直接升级 zzupy | APK +20–40MB；商业授权；启动慢；后台不可靠 | 不推荐 |
| **B. Kotlin 复刻** | 原生、可控、无依赖风险 | 需逐接口翻译（**但接口很少**） | **推荐** |
| C. 混合 | Kotlin 跑主流程，Python 做改版时的快速验证 | 需两套环境 | **推荐作为辅助** |

**推荐 B + C**：Android 里用 Kotlin 实现；学校改版时，先用 Python + zzupy 快速定位变化点，再改 Kotlin。这样"接口变了"这件事的排查成本能压到最低。

### 9.2 空调费：**勘误** —— 换成房间号即可，`utilityType` 根本不用改

> ⚠️ **本节初稿的结论是错的。** 初稿推断"空调费 = 换一个 `utilityType` 取值"，需要抓包确定。**该推断已被 [Elykia093/ZZU-Electricity-Monitor](https://github.com/Elykia093/ZZU-Electricity-Monitor) 的实现证伪。**

该项目的 `monitor.py` 核心逻辑（直接使用 zzupy 现成方法）：

```python
light_balance = ecard.get_remaining_energy(room=settings.light_room)   # 照明
ac_balance    = ecard.get_remaining_energy(room=settings.ac_room)      # 空调
```

`get_remaining_energy()` 内部**固定** `utilityType: "electric"`（zzupy 源码 line 667）。两个调用**唯一的差别就是 `room` 参数**。

**正确结论**：

- **同一个 endpoint**：`https://ecard.v.zzu.edu.cn/server/utilities/account`
- **同一套参数**：`utilityType` 恒为 `"electric"`
- **唯一差异：房间号** —— 照明和空调是**两套独立的电表**，房间号不同

→ **空调费的实现成本是 0**。不需要抓包、不需要新参数，直接调现成的 `get_remaining_energy(room=AC_ROOM)`。

配套证据：房间查询器数据里，每个楼栋的单元分类就是「照明房间」和「空调房间」两类（见第十三章）。

**P5（空调费）：从"极低风险待确认"降级为"零成本、已验证"。**

### 10.4 ⚠️ 决定性发现：签到闭环在物理世界，App 无法实现

预约规则原文（`/v4/index/bookingRules`）：

> 图书馆外的读者预约当日座位，需在当日 **8:00 前或预约成功后 30 分钟内通过门禁闸机刷卡（刷脸）入馆**，系统自动完成签到。
> 未选择"临时离开"且**未通过门口闸机刷卡（刷脸）出馆**的读者将被记"未签离"违规 1 次。
> **以上 4 种违规累计满 3 次将被暂停使用图书馆的座位预约权限 7 天。**

**含义**：座位预约最关键的"签到 / 签离"环节依赖图书馆物理闸机（刷卡/刷脸），**第三方 App 永远无法代替**。用户用你的 App 约了座，仍然必须本人走到图书馆刷脸。

→ 因此这个模块的产品定位是**"辅助工具"，不是"完整替代"**。

### 10.5 另一个高风险点：违规惩罚落在用户头上

- 预约时间：**早上 7 点后**可约当日或次日 → 这是抢座高峰，也是风控最严的时段
- 违规类型 4 种（未签到 / 未签离 / 临时离开未刷卡 / 临时离开超时）
- **累计 3 次停用座位预约权限 7 天**

→ **自动化预约必须绝对禁止**：脚本约了座而用户没去，被罚的是用户自己。

### 10.6 认证

规则原文：

> 空间预约系统的用户名及密码与**学校统一身份认证平台**一致，用户名为学号，密码为学校统一身份认证密码。

→ **可复用已有的 CAS 令牌流程**。前端也印证了这点：存在独立的 `cas.1780450282721.js`，sessionStorage 里有 `isCas`、`casAuth`、`token`、`UserInfo`、`verifyLogin` 等键。

### 10.7 附带发现：这是通用商业产品

`/v4/index/bookingRules` 的"物品招领"规则里残留了**"浙江理工大学图书馆"**字样——说明该系统是厂商产品，ZZU 只是客户，**其他采用同款系统的学校有可参考的同类实现**。厂商未署名。

### 10.8 结论与建议

**实现难度：从"高风险黑盒"降为"路径清晰"。**

| 维度 | 结论 |
|---|---|
| 校外可达 | ✅ 有（**只能走 HTTP:80**，443 校外被拒） |
| 逆向成本 | ✅ **极低**——H5 + 未混淆 JS，88 个接口已到手，无需抓包/反编译 |
| 认证 | ✅ 统一身份认证，可复用 CAS 流程 |
| 座位查询 | ✅ 接口明确 |
| **签到闭环** | ❌ **无法实现（依赖物理闸机）** |

**建议分三层，只做前两层：**

**层 1（推荐做，低风险高价值）——只读 + 提醒**
- 查实时座位占用（`/v4/Space/map`）→ "现在还有没有座"
- 查我的预约记录（`/v4/member/seat`）→ 到期提醒
- **临时离开 60 分钟倒计时**（与番茄钟天然契合）
- **违规风险提醒**（未签到/未签离，累计 3 次停 7 天）
- 一键取消预约（规则明确支持，且能避免违规）

**层 2（可做但慎重）——手动预约**
- 用户主动选座 + 提交（`/v4/space/pick` → `/v4/space/confirm`）
- 前提：**纯手动、用户每次主动触发，不做任何定时/自动**

**层 3（绝对不做）——自动化抢座**
- 早上 7 点抢座场景 + 违规惩罚落在用户头上 + 属"占座脚本"风险区

**另一个必须注意的点**：校外只能走 HTTP 明文，意味着**登录凭据在网络上明文传输**。这是校方服务的限制。按"首次登录拿 token、之后只存 token"的设计，明文暴露面仅限首次登录那一次——这进一步支持不要存密码。

**最终判断：值得做，但排最后，且先只做层 1。**

### 11.6 容易忽略的问题清单

1. **番茄钟时长 vs 闸机记录会打架**：番茄钟记 9:10–10:00（50 分钟），闸机记 9:00–12:00（3 小时）。建议**分开显示**——"有效学习时长"（番茄钟）与"在馆时长"（闸机），不要合并成单一数字。
2. **热力图会撒谎**：某天没打开 App 也没开番茄钟 → 显示 0 小时，但用户实际学了。**"数据缺失" ≠ "没学习"**。需用不同视觉区分"无记录"与"零时长"。
3. **"周"的定义**：教学周 vs 自然周？假期、调休、跨学期如何切分？建议以自然周为统计单位，但支持对齐教学周显示。
4. **番茄钟在 Android 上的计时精度**：Doze / 省电会冻结计时器。必须用 `SystemClock.elapsedRealtime()`，并以"开始时间戳 + 计划时长"计算，**不能靠自增计数器**。长番茄（90 分钟）尤其明显。需前台服务 + 精确闹钟权限，用户会看到常驻通知。
5. **国产 ROM 杀后台**：小米/华为/OPPO/vivo 需引导加入电池优化白名单，否则"低电量提醒""预约到期提醒"会静默失效。
6. **数据只存本地 = 换手机全丢**：历年学习时长、用电历史都会消失。是否做导出/备份？**这是现在就要决定的产品问题**，它影响数据模型（主键与时间戳规范）。
7. **通知权限**（Android 13+）可能被拒 → 需要 App 内红点等降级 UI。
8. **两个费用账户的房间 ID 可能不同**：电费与空调费各有默认房间，数据模型要支持"一类型一房间"。
9. **多端登录冲突**：用户在官网与 App 同时操作时，CAS 的 `userOnlineDetect` 机制可能导致互相踢下线。
10. **长期维护成本**：3 套完全独立的系统（教务 / 一卡通 / 图书馆），任何一套改版都可能让某模块挂。需要解析层容错 + 远端配置热修 + **每模块独立降级**，不能一个模块挂掉拖垮整个 App。
11. **合规边界随分发方式变化**：自用风险低；一旦开源或给同学用，就从"个人工具"变成"向他人提供访问校方系统的工具"，性质不同（长沙理工大学那份声明正是针对此）。当前设计（不存密码、只存自己的 token、纯本地、不经中转服务器）在自用场景是干净的，**但如果要分享，需重新评估**。
12. **请求量叠加**：多模块各自定时轮询会叠加请求量、更易被识别。建议集中在一次"刷新"里。
13. **座位预约天花板要提前接受**：签到靠闸机，App 只能做到"看空座 + 预约 + 提醒 + 取消"，不宜作为核心卖点。

## 十二、座位预约记录接口：已确认可用（2026-09-19）

用户澄清：之前看到的"进出馆时间"其实是**预约记录里显示的信息**，不是闸机记录。据此核查，结论如下。

### 12.1 接口确认

定位到 `assets/sear-record.1780450282721.js`（文件名有笔误，实为 seat-record）中的接口定义：

```js

```

### 12.2 返回字段（从渲染代码 `seat-record*.js` 中提取）

| 字段 | 含义 |
|---|---|
| `area_name` | **地点（区域 / 馆舍）** |
| `seat_name` | **座位名** |
| `seat_id` | 座位 ID |

### 12.3 可以取历史记录

列表页 chunk 中出现 `page`、`limit`、`pageSize`、`total`、`status`、`type` 等参数：

- **分页参数存在** → 可以翻页拉取历史预约记录
- 状态筛选中出现标签：**未签到**、状态异常、候补失败/中/成功、用户取消候补

另有记录详情页 `assets/seat-record-details.*.js`（`/v4/space/detail`）与候补页 `seat-wait`。

### 12.4 ⚠️ 但"自习"与"图书馆"仍应分离——理由不是"拿不到"，而是"语义不同"

| 数据 | 语义 | 可信度 |
|---|---|---|
| 番茄钟时长 | 用户**主动声明**的专注时长 | 用户自证 |
| 预约记录时段（`beginTime`–`endTime`） | 用户**预约占用的**时段 | **不等于实际在馆**（签到靠闸机，可能爽约） |

因为签到/签离依赖图书馆闸机，预约记录里的时段是**预约时段**，不是**实际在馆时段**。两者合并成一个"学习时长"会失真。

**建议**：
- 番茄钟 = "有效学习时长"
- 预约记录 = "图书馆行程 / 预约时段"，单独展示（时间轴、记录列表）
- **不要合并成单一数字**

### 12.5 一个实用设计点

预约记录状态里存在**「未签到」**。用它过滤：

- 只统计**已正常完成**的记录作为"图书馆时段" → 避免把爽约也当成学习时间
- 同时可以把"未签到/未签离"作为**违规风险提醒**（累计 3 次停用 7 天）

### 12.6 该模块可行性结论

| 项 | 结论 |
|---|---|
| 拿到预约记录（地点/日期/起止时间/状态） | ✅ **可行**，接口与字段已确认 |
| 翻页取历史 | ✅ 支持（分页 + 状态筛选） |
| 认证 | ✅ 统一身份认证，可复用 CAS |
| 校外可用 | ✅ 有（**走 HTTP:80**，443 校外被拒） |
| 实际在馆时长（闸机记录） | ❌ 无接口（未找到，且整个 H5 无"入馆"字样） |

→ **用户提出的"如果这部分可以获得，可以考虑后续制作"——条件成立，建议纳入计划，但排在只读查询层。**

### 13.5 可借鉴的工程实践

1. **低频轮询**：每 4 小时一次。比本文建议的 30–60 分钟还稀疏，**进一步印证"电量数据更新很慢，高频轮询无意义"**。
2. **松耦合的异常匹配**（很聪明，值得抄）：

```python
# 按"类名"匹配可重试异常，刻意不 import zzupy 的具体异常类：
# 即使 zzupy 升级后调整了异常模块路径或重命名了类，本模块也不会因 ImportError 整体崩溃；
# 最坏情况只是某个被改名的异常不再触发重试（安全降级）。
RETRYABLE_EXCEPTION_NAMES = frozenset({"LoginError", "NetworkError", "NotLoggedInError", ...})
```
   → 在 Android/Kotlin 里同理：**按错误码/HTTP 状态判断可重试**，不要硬绑具体异常类型。
3. **重试策略**：5 次尝试、指数退避 15s → 120s、超时 10s。
4. **认证失效后的重试**：查询失败 → 关闭并重建一卡通客户端 → 重试一次（对应我们设计的 401 单飞刷新）。
5. **房间号格式校验**：`--` 恰好一次、拆开后 4 段全为数字（如 `99-1--1-101`）。
6. **阈值设计**：低电量 10 度、充足 100 度，可直接沿用。
7. **可视化清单**：最近 30 条、按月趋势、年度总结、每日/月度统计 + 热力图——正是我们需求④想要的。

### 13.6 不建议照搬的部分

| 它的做法 | 为什么不照搬 |
|---|---|
| 用 `PASSWORD` 作为 AES-256-GCM 的加密密钥 | Actions 场景下的妥协。Android 里应使用 **Android Keystore / EncryptedSharedPreferences**，绝不用密码派生密钥 |
| 数据存 JSON 文件、按月切分 | Android 里应用 **Room**（可查询、可聚合、可迁移） |
| GitHub Actions + 静态页面架构 | 与"端到端直连、不经中转"的 App 目标不符；它的前端是 ECharts 网页，不是 App UI |
| 逐级 `get_room_dict()` 查房间 | 改为用 13.3 的静态数据，省一轮调用 |

## 十四、空教室接口：尝试免抓包路线（失败）+ 抓包方案

用户要求确定空教室（唯一还需要抓包的模块）。先尝试了几条**不需要抓包**的路线，结果如下。

### 14.1 有价值的负面结果：郑大没有部署树维经典网页版

搜索发现 [Ares-Gao/WeCourseService](https://github.com/Ares-Gao/WeCourseService)（**树维教务系统接口封装**，多语言 SDK）。其 README 明确支持「**查询公共空闲教室**」，并且：

> 该接口走树维公共页面 `publicFree!search.action`，**不区分学生或教师账号，也不要求登录**。

如果郑大部署了经典 EAMS 网页版，这个接口就能直接白嫖。**实测结果是走不通**：

| 请求 | 结果 |
|---|---|
| `GET /eams/homeExt.action` | **404**（nginx） |
| `GET /eams/login.action` | **404** |
| `GET /eams/publicFree!search.action?DateBegin=...` | **404** |
| `POST /eams/publicFree!search.action`（表单） | **404** |
| `GET /eams/publicFree.action` | **404** |
| `GET /eams/freeRoom!search.action` | **404** |
| `GET /` | 301 → `/eams`，但 `/eams` 与 `/eams/` 均 404 |

**结论：郑大只部署了"新版 EAMS"（`eams-door` / `eams-micro-server` 微服务，App 专用），没有经典 Struts2 网页版。** 这印证了用户的观察——网页端找不到空教室功能。

→ **空教室的 endpoint 只能从 App 抓包获得。**

### 14.2 但挖到了接口语义：抓包时"照着找"而不是"大海捞针"

WeCourseService 暴露了树维空闲教室的**请求参数与返回结构**。新版 REST API 的参数命名会变，但语义大概率一致：

**请求（旧版 WebSocket 封装格式）**：

```json
{
  "Type": "freeroom",
  "DateBegin": "2026-06-05",
  "DateEnd": "2026-06-05",
  "RoomTimeType": "0",
  "TimeBegin": "1",
  "TimeEnd": "2"
}
```

| 参数 | 含义 |
|---|---|
| `DateBegin` / `DateEnd` | 日期范围 |
| `RoomTimeType` | `0` = 按小节；`1` = 按 `HH:mm` 时间 |
| `TimeBegin` / `TimeEnd` | 小节序号或时间 |

**返回**：

```json
[
  { "Index": "1", "Name": "50404", "Building": "5号楼", "Campus": "南区",
    "TypeName": "琴房", "Capacity": "10" }
]
```

→ 教室名 / 楼栋 / 校区 / 教室类型 / 容量。

**这两个清单直接决定了抓包要找什么**：一个带日期范围 + 节次（或时间）范围的请求，返回带 building / campus / capacity 的教室列表。

### 14.3 抓包方案（按成本从低到高）

#### 第 1 步（首选，5 分钟，成本最低）：Chrome 远程调试 WebView

**如果 App 的「教务系统（新）」是 WebView 加载的 H5**，可以完全跳过代理和证书：

1. 手机开启「开发者选项 → USB 调试」，USB 连电脑
2. 电脑 Chrome 打开 `chrome://inspect/#devices`
3. 手机 App 里打开「空闲教室」页面
4. 若列表里出现该 WebView → 点 `inspect` → **Network 面板直接看到所有 XHR**，还能看它的 JS 源码

**优点**：不需要装 CA 证书、**不受 SSL Pinning 影响**、能看到 JS 源码（等于可以直接读出接口清单，像图书馆那样）。
**前提**：App 的 WebView 未关闭调试开关。release 版常会关，但不少国产 App 忘了关——**值得先试，成本几乎为零**。

#### 第 2 步：手机端 VPN 抓包 App（免 root 通用方案）

推荐 **Reqable** 或 **HttpCanary（小黄鸟）**：

- 手机直接跑，走 VPN 模式，**不需要把 CA 装成系统证书**
- 能抓绝大多数 App 的明文 HTTP(S)
- 支持按 App 过滤（只抓豫见郑大，减少噪音）
- 抓到的请求可以直接导出 HAR 或复制 cURL

#### 第 3 步：mitmproxy / Reqable 桌面版 + 手机代理（有 root 更稳）

1. 手机与电脑同一局域网（或电脑开热点，手机连）
2. 手机 WiFi 设置里手动填代理：`电脑IP:8080`
3. 电脑跑 `mitmproxy`（或 Reqable/Charles）
4. 手机浏览器访问 `mitm.it` 安装 CA 证书
5. **Android 7+ 关键坑**：用户证书默认不被 App 信任（`targetSdk ≥ 24` 只信系统证书）
   - 有 root：把 CA 装进系统证书目录，或刷 Magisk 模块（MagiskTrustUserCerts / AlwaysTrustUserCerts）
   - 无 root：回到第 2 步

#### 第 4 步（只在被 SSL Pinning 挡住时才需要）

⚠️ **豫见郑大加了「爱加密企业版」壳**（zzupy 作者验证过），**大概率存在证书绑定**。失败特征：App 页面转圈/加载失败，代理日志只看到 CONNECT 后立刻断开。

- **有 root**：Frida + `frida-android-unpinning` 之类脚本 hook 掉证书校验
- **无 root**：**LSPatch** 重打包 + 注入模块（免 root 的 Xposed 方案）——zzupy 作者提到过这个思路
- ⚠️ 重打包 APK 有额外风险（可能被检测、可能影响登录），**放在最后考虑**

### 14.4 抓包特征清单（找到哪个就是它）

在 Network 里筛选这几类关键词：

| 关键词 | 说明 |
|---|---|
| `classroom` / `room` | 最可能 |
| `free` / `empty` / `vacant` | 空闲 |
| `classroom` + `free` | 组合 |
| `eams-micro-server` / `eams-door` | 确认是新版 EAMS 的请求 |

**判定标准**：请求里带 `date`（或 DateBegin/DateEnd）+ 节次或时间范围，响应是一串带 `building` / `campus` / `capacity` / `name` 的 JSON 数组。

### 14.5 抓到之后需要回传什么

只需三样东西（**不要发账号密码、token、Cookie**）：

1. **完整请求**：URL、Method、请求体/查询参数、以及必要的请求头（**token 值打码**）
2. **完整响应**：一条成功的 JSON（可截断，但要保留结构和字段名）
3. 顺便确认：这个请求是否**需要登录态**（看它有没有带 Authorization / Cookie）

拿到这三样我就能：确定 endpoint、写解析层、判断能否本地推导（例如返回到的是"教室占用表"还是"空闲列表"，决定要不要本地反算）、并给出缓存策略。

5. 端口转发 + 直接讲 CDP 协议（Node 24 内置 WebSocket）：
   ```
   adb forward tcp:9333 localabstract:webview_devtools_remote_7713
   # 然后 http://127.0.0.1:9333/json/list 拿 webSocketDebuggerUrl
   ```
6. 用 `Runtime.evaluate` 在 WebView 里执行 JS、用 `Page.getFrameTree` 找 iframe、用 `Network.enable` 捕获真实请求

### 15.2 教务是 uni-app H5（关键结构）

```
外层：https://jwxt.zzu.edu.cn/uniapp/index.html?idToken=<JWT>
        └─ 帧 #/pages/webview/webview?url=...eams-room-occupy-app/index.html
             └─ iframe：https://jwxt.zzu.edu.cn/eams-room-occupy-app/index.html   ← 空教室模块
```

- 外层是树维的"超级 App"外壳（uni-app），带 tabbar（home/message/schedule/mine 等）
- **空教室是独立 H5 微应用**：`eams-room-occupy-app`
- 页面代码在懒加载 chunk：`/eams-room-occupy-app/static/js/pages-index-index.c5761235.js`

### 15.3 鉴权（重要）

```js
headers: {
  Authorization: localStorage.getItem('X-Id-Token') || localStorage.getItem('userToken'),
  'Content-Type': 'application/json;charset=UTF-8',
  Accept: 'application/json'
}
```

- 外层 H5 通过 **URL 查询串** 接收 `idToken`（JWT，RS512，签发者 `cas.s.zzu.edu.cn`），存进 `localStorage['X-Id-Token']`
- localStorage 的键：`X-Id-Token`、`idToken`、`token_key`、`baseUrl` 等
- ⚠️ 注意：H5 用的是 `idToken`；而 zzupy 对同一网关用的是 CAS 的 `userToken`，**两者都被接受** → **Android 端不需要单独取 idToken，直接复用已有的 CAS `userToken` 即可**

### 15.6 ⚠️ 关键结论：返回的是「占用表」，不是「空闲列表」

**必须本地反算空闲**（与 14.2 对树维语义的预判一致）：


- 时间用 **HHmm 整数**（`800` = 08:00）+ 友好的 `startTimeString`

## 十六、数据来源性质与校区影响（2026-09-19）

### 16.1 每个数据源的性质：官方实时 / 第三方静态 / 本地计算

用户提问"是不是大部分接口都能实时更新"。答案是**是的，只有一个例外**：

| 数据 | 来源 | 能否实时更新 |
|---|---|---|
| 课表 | 教务 EAS API（**官方**） | ✅ 每次调用都是最新，调课会反映 |
| **空教室** | 教务 EAS API（**官方**） | ✅ 按 `date` 查任意日期，实时 |
| 节次时刻表 | 教务 EAS API（**官方**） | ✅ 实时（内容几乎不变） |
| 校区 / 楼栋 / 楼层 / 教室类型 | 教务 EAS API（**官方**） | ✅ 实时 |
| 校园卡余额 | 一卡通 API（**官方**） | ✅ 实时 |
| 校园卡交易记录 | 一卡通 API（**官方**） | ✅ 实时（增量拉取） |
| 寝室电费 / 空调电费 | 一卡通 API（**官方**） | ✅ 实时（每次是当前读数） |
| 图书馆座位占用 | 图书馆 API（**官方**） | ✅ 实时（秒级变化） |
| 图书馆预约记录 | 图书馆 API（**官方**） | ✅ 实时 |
| **电费房间查询器（0.7MB JSON）** | ⚠️ **第三方（Elykia093）整理的静态文件** | ❌ **静态，可能过期** |
| 热力图 / 周月年总结 / 每日用电 | **本地计算** | — 不涉及"更新" |

**唯一非官方来源是电量房间查询器那份静态 JSON。** 建议做成可远端更新，并抽样校验。

### 16.2 ⚠️ 但"能实时查" ≠ "应该高频查"

"实时"是**能力**，"按需低频"是**策略**。每个数据的推荐频率见 11.4 与 4.2 节：

- 课表 / 节次表：一学期变几次 → 低频
- 电量：服务端本身小时级才更新（11.1 实证：15 分钟内 16 条读数完全相同）→ 30–60 分钟
- 座位：秒级变化，但**只在用户打开页面时查**，不后台轮询
- 空教室：当天数据会因临时借用变化 → 缓存 10–30 分钟

### 16.3 校区影响矩阵

郑大有 5 个校区（`/room/place/campus` 实测）：主校区(id=2)、南校区(3)、北校区(4)、东校区(5)、南校区·河南音乐学院(6)。

| 模块 | 受校区影响 | 细节 |
|---|---|---|
| **空教室** | ✅ **必须选** | `campus` 接口返回 5 个校区；`/room/place/building` 的 `campusAssoc` 是**必填**参数 |
| 节次时刻表 | ❓ 大概率全校统一 | `course-units` **没有校区参数** → 推测一套作息。但存在 `changeStartTime`/`changeEndTime` 字段（当前为 0），可能用于作息调整。**建议用主校区验证并留意** |
| 课表 | ⚠️ 间接 | 数据不分校区，但课程**地点**可能在别处；若跨校区选课，"下一节课"的时间轴要考虑通勤 |
| 电费 / 空调费 | ✅ 有影响 | 房间查询器分 6 个校区文件（`99`=主校区 479KB，`101`–`105` 其他）。但**用户只需自己宿舍那一个房间号**，选一次即可 |
| 校园卡余额 / 交易 | ❌ 无影响 | 全校一张卡 |
| **图书馆座位** | ✅ **有影响（分区域）** | 接口用 `areaId` / `floorId` / `roomId` 三级组织，**座位图按"区域"划分** → UI 需提供区域选择 |
| 图书馆预约记录 | ✅ 有影响 | 记录里的 `area_name` 会体现是哪个区域 |
| 番茄钟 / 热力图 / 总结 | ❌ 无影响 | 纯本地 |

### 16.4 结论：优先主校区完全可行

校区影响是**局部的、可控的**，且集中在两处：**空教室（必须选校区）** 和 **图书馆（必须选区域）**。

推荐做法：

1. App 设置里加一个「**默认校区**」选项，**默认主校区**，可切换
2. 空教室页顶部可切校区，默认取设置值
3. 图书馆区域用选择器（区域列表从接口拉），默认选一个
4. 电费房间选一次即可，与校区几乎无关
5. **代码上把校区做成一个常量 / enum**，所有 provider 接受一个 `CampusContext`（默认 `MAIN`）。将来要支持别的校区只改配置、不改逻辑

**主校区优先的实际好处**：用户本人就在主校区（房间 `99-16--32-8101` = 主校区松园15号楼）；主校区的房间查询器数据也最完整（479KB，其余校区 4–104KB）。

### 16.5 两处澄清（本轮核查中发现的）

1. **「请选择地区」不是图书馆的业务字段**。它出现在 Vant 组件库内置的地址编辑 i18n 文案里（`vanAddressEdit.areaEmpty`）。图书馆的空间层级实际是 `areaId` → `floorId` → `roomId`。
2. **「入馆查询」菜单项存在，但 `path:""`（未配置）**。图书馆主 bundle 的菜单表里有：
   ```
   {id:"5", name:"入馆预约", enname:"Admission Reservation", path:""}
   {id:"8", name:"入馆查询", enname:"Library entry Query",     path:""}
   ```
   → **这两个功能入口存在但未启用**。这解释了为什么 88 个接口里找不到"入馆记录"接口——**功能本身没做**（同类的「设备租借」也是空路径）。
3. **补扫了主入口 bundle**（此前只扫了 212 个 chunk，漏了入口文件）：**没有发现新接口**，88 个的清单是完整的。
