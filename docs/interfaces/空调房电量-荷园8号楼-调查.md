# 空调房电量：荷园8号楼「一户三空调房只显示两间」调查

> 2026-10-28 用户报告：荷园8号楼 c单元01户 有**三个空调房间**，界面却**只显示两个**，
> 不清楚别的户是否同样有问题。报告人自称住 荷园8号楼 301，应是「第 3 户」。
> **根因已定（用户截图确认）：数据没有任何问题，是 RoomPickerDialog 确认页的
> 空调户芯片行用单行 `Row` 装不下 3 颗长标签芯片 —— 第三颗被压成零宽，
> 看不见却仍可点击。已改为 `FlowRow` 换行排布修复。**

## 1. 现象与口径

- 「c单元01户」是学校 H5 的叫法：显示名由
  `bigAreaName + areaName + buildingName + unitName + levelName + roomName + subAreaName`
  拼出（见 `_research/ecard_probe/c_pages_payment-electrictyFees-*.js`），
  我们的房间资产里没有 name 字段，这个叫法不进我们的数据。
- 荷园2–9号楼是「一间房每人一个空调表」（`acRule=suffix`，acPerRoom=3）。
  选房确认页按资产出芯片：`3011（第 1 户）/3012（第 2 户）/3013（第 3 户）`。

## 2. 数据侧结论（已全量核对）

- 资产 `app/src/main/assets/rooms.json` 与上游快照（`_research/rooms_campus/99.json`，
  ZZU-Electricity-Monitor）**等价**；上游 2026-10-28 重新拉取与 9 月副本一致。
- 荷园8号楼（area 99, building 92, 灯 unit 203, 空调 unit 204）：照明 36 × 空调 108，
  **每个照明号 ×3 全在**：301 → 3011/3012/3013 完整。
- 全库审计（上游 6 区域 vs assets）：14711 灯间 / 14793 空调位，仅 6 处出入
  （柳园17留学生补录、洛阳 105 楼栋拆分口径），与荷园无关；
  **没有任何一条规则"凭空少给"**。`RoomCatalogTest` 全绿。

## 3. 根因（截图坐实）与修复

报告人截图：确认页标题 "确认房间 / 荷园8号楼 301"，文案写明"这间房有 3 个空调户"，
但芯片行只见 `3011（第 1 户）`、`3012（第 2 户）` 两颗 —— 第三颗不可见；
而下方"空调房间 ID：99-92--204-3013"已出现（第三颗芯片其实存在）。

Compose 里的机制：`ConfirmStep` 的芯片是**无权重单行 `Row`**，三颗芯片、
标签都是「表号 +（第 N 户）」共约 10 个全角字符。前两颗占满宽度后，
第三颗被按**零宽**测量：一根竖条里逐字换行，变成一根"看不见的高柱"——
正因为它有 Material 最小可点目标，空白处盲点一下就选中第 3 户；
视觉上则是"芯片行下面一大块空白 + 只显示两个"。

修复（`RoomPickerDialog.kt` `ConfirmStep`）：芯片行 `Row` → `FlowRow`
（`horizontalArrangement/verticalArrangement = spacedBy`），放不下自动换行，
3–4 颗芯片全部可见可点；附 kdoc 记录这次事故的机制以免回退。
全仓同类排查结果：其余 FilterChip 行要么已是 `FlowRow`（Room/Focus/PlanEditor/Card），
要么是短标签固定枚举（外观深浅色 3 项、电量区间 7/30/90 天、补录类型 2 项），无同类风险。

## 4. 遗留的可选排查工具（本次已不再必需）

当初为"学校侧实况"准备的在线探测脚本 `_research/probe_he8_ac.mjs`（作者本机，不入库）：
树探查 + 空调行代码穷举（`3011..` 候选逐个问 `/utilities/account` 是否返回 quantity），
输出与资产逐户对比。用途现在只剩一个：**若干年后快照过期**（学校新建/拆分表计）
时的多楼快速核对。届时用法：

```bash
node probe_he8_ac.mjs <accessToken> [--buildings 荷园8号楼,荷园7号楼] [--full-brute]
```
