# ZZUPocket — 开发流程与阶段计划

> 项目名：**ZZUPocket**（显示名）
> 建议包名：`io.github.<你的GitHubID>.zzupocket`（用 GitHub ID 是诚实的反向域名，不需要自己拥有域名）
> 配套：`郑大校园助手-功能与工具清单.md`（范围基线）、`郑大校园助手-接口现状核查.md`（接口）、`郑大校园助手-Android接入设计.md`（架构）、`郑大校园助手-UI与登录设计.md`（界面）

---

## 一、为什么选这套流程

### 1.1 项目特征（决定流程）

| 特征 | 含义 |
|---|---|
| **单人开发、业余时间** | 任何团队流程（Scrum/评审/站会）都是纯开销 |
| **无 deadline、无外部客户** | 不需要按时间盒倒排，按风险和价值排序即可 |
| **最大的不确定性在"外部系统"** | 学校接口随时可能改版，且不受你控制 |
| **架构复杂度集中在认证与令牌生命周期** | 不是功能多，是"会话"难 |
| **最大的失败模式是"烂尾"** | 个人中大型项目的头号杀手 |
| **可以真机天天用** | 这是最大的优势——能 dogfooding |

### 1.2 结论：**Walking Skeleton + 垂直切片 + 迭代增量**

不采用 Scrum / 完整 XP / GitFlow——单人项目里这些流程的组织开销大于收益。

采用这套的三个理由：

1. **Walking Skeletch（先走通骨架）**
   先用**最薄的一条端到端链路**（登录 → 网络 → 解析 → Room → UI）把架构验证掉。
   本项目的架构复杂度几乎全在认证上，所以**必须最先证明"登录能持久、令牌能刷新、后台不死"**，而不是先堆功能。

2. **垂直切片（Vertical Slice）**
   一次做完"一个功能的完整链路"，而不是"先把所有网络层写完再写 UI"。
   避免出现"底层都齐了但屏幕上没东西"的中间态——那是最容易失去动力的状态。

3. **迭代增量**
   每轮结束都产出**一个能装上、能每天用的 APK**。这是对抗烂尾的唯一可靠机制。

### 1.3 六条具体做法

| # | 做法 | 说明 |
|---|---|---|
| 1 | **一次只做一条垂直切片** | UI → ViewModel → Repository → Provider → Room，一条打通再下一条 |
| 2 | **每阶段必须产出可安装 APK + git tag** | 装到自己手机上，**强制自用一周**再进下一阶段 |
| 3 | **先 Mock 后真实** | 每个远程 Provider 先写返回 fixture JSON 的 Mock 实现，UI 立刻能跑；真实实现就位后再切 |
| 4 | **Fixture 快照测试** | 把真实响应存成 JSON 文件，解析层写单元测试。**学校改版时，改 fixture 重跑就知道哪一层坏了** |
| 5 | **接口变更响应是一等公民** | 见 1.4，配好流程后单次改版响应 < 1 小时 |
| 6 | **Trunk-based** | 直接在 `main` 开发，功能大就开短分支；每阶段打 tag（`v0.1.0`、`v0.2.0`…） |

### 1.4 接口改版的应急流程（目标 < 1 小时）

这是这个项目**唯一会反复发生**的维护动作，所以现在就把流程固化：

```
① 发现功能挂了（自己用出来的，或数据明显不对）
        ↓
② 用 _research/ 里的 adb + CDP 脚本重新连 WebView
   （打开对应页面 → adb forward → 读 JS / 抓真实请求）
        ↓
③ 对比 git 里的 fixture：「接口路径变了」还是「字段名变了」还是「鉴权变了」
        ↓
④ 改解析层 或 改远端配置（URL/字段路径抽成了可下发的 JSON，多数情况不用发版）
        ↓
⑤ 更新 fixture + 补快照测试
        ↓
⑥ 出 hotfix APK，打 tag
```

**所以有三件事必须从 P1 就做**：fixture 目录、宽松解析、远端配置。

### 1.5 每个阶段的完成定义（DoD）

一个阶段算完成，必须同时满足：

- [ ] 功能在**真机**上可用（不是只在模拟器/预览里好看）
- [ ] **断网 / 令牌过期时表现正确**：不白屏、不崩、显示"数据截至 XX:XX"
- [ ] 解析层有 **fixture 快照测试**
- [ ] 打了 **git tag** + 写了 CHANGELOG 一行
- [ ] **自己用满一周**，把问题记进 issues

### 1.6 明确不做的事

| 不做 | 原因 |
|---|---|
| CI 流水线（GitHub Actions 跑构建） | 单人项目价值低；lint/test 本地跑就够 |
| 追求测试覆盖率 | 只测**解析层 + 关键业务逻辑**（电量差分、教学周换算、空闲反算） |
| 完整的多模块架构 | 单模块 + 清晰分包足够 |
| 写详细设计文档 | 本文 + 四份配套文档已经是上限 |
| 上架应用商店 | 需软著+备案，且"抓校方数据"类易被下架 |

## 二、开发阶段

### 总览

| 阶段 | 名称 | 预估（专注人天） | 主要风险 |
|---|---|---|---|
| **P0** | 脚手架 | 0.5–1 | 低 |
| **P1** | **Walking Skeleton**（认证 + 电费最小闭环） | 2–3 | **中高** |
| **P2** | 课表 | 3–5 | 中 |
| **P3** | 专注（番茄钟 + 热力图）+ 桌面小组件 | 2–3 | 低 |
| **P4** | 一卡通完整 | 2–3 | 低 |
| **P5** | 空教室 | 2–3 | 中 |
| **P6** | 图书馆 | 2–4 | 中 |
| **P7** | 汇总统计 + 备份 + 打磨 | 3–5 | 低 |
| **P∞** | 维护（接口改版响应） | 持续 | — |

**合计约 17–27 专注人天**。业余时间要乘 1.5–2 的系数 → **约 1–2 个月**。

---

### P0 · 脚手架（0.5–1 天）

| 项 | 内容 |
|---|---|
| 目标 | 工程能编译、能装到手机、能跑 |
| 产出 | Gradle 工程（Kotlin 2.x / AGP / `libs.versions.toml`）+ Compose + Hilt + Navigation Compose + 4 个 tab 占位页 + Mock/Remote 数据源开关 |
| DoD | 手机上装上，4 个 tab 能切，深色模式跟随系统 |
| 风险 | 低。唯一坑是 AGP/Kotlin/Compose 版本搭配 |

---

### P1 · Walking Skeleton：认证 + 电费最小闭环（2–3 天）⭐ 最关键

| 项 | 内容 |
|---|---|
| **目标** | **用一个真实远程功能，把全链路打通，验证最大的技术风险** |
| 为什么用"电费"当骨架 | 它是最简单的远程功能：单个接口、参数固定、**已实测可用**；但它走的是**完整的 CAS → 一卡通两级令牌链**，正好把认证链路验掉 |
| 产出 | ① 登录页（学号+密码+短信验证码）<br>② **令牌加密存储**（EncryptedSharedPreferences，只存 token 不存密码）<br>③ 401 单飞刷新 + 重试一次<br>④ 请求头复刻 + 限流拦截器<br>⑤ 寝室电费单页 + "数据截至 XX:XX"<br>⑥ **Mock 数据源 + fixture 目录 + 快照测试**<br>⑦ **登录诊断页（雏形）** |
| **DoD（本阶段最重要的三条）** | ① **登录一次后能长期使用**（杀掉 App 重开仍在登录态）<br>② **断网时显示上次电量而不是白屏**<br>③ 令牌过期时能自动刷新，刷新失败才引导重登 |
| 风险 | **中高**。认证是本项目最大的不确定性：令牌寿命、刷新策略、后台是否会掉登录态、MFA 可信设备是否生效 |
| 备注 | ⚠️ 首次登录会把你手机上的豫见郑大踢下线一次（`userOnlineDetect`），登录页必须明确告知；登录后引导去[安全中心](https://authx-service.s.zzu.edu.cn/security-center/eqIP-management)把 deviceId（用包名）设为可信设备 |

**P1 通过后，项目就已经"不会烂尾"了**——因为最坏情况下你也有一个能查电费、且架构完整的 App。

---

### P2 · 课表（3–5 天）

| 项 | 内容 |
|---|---|
| 目标 | 拿下最高日常价值的功能，同时铺好「今天」页的地基 |
| 产出 | ① EAS Provider（学期列表 / 当前学期 / 整学期课表 / 周次换算）<br>② **7×10 周网格**（最难的 UI，先做纯文本格子版本，再迭代）<br>③ `HorizontalPager` 左右切周<br>④ 教学周标识 + 日期↔周次<br>⑤ 课程详情 `ModalBottomSheet`<br>⑥ **节次时刻表**（`/room/system/course-units`）<br>⑦ 「今天」页的课表时间轴 + **"现在在干什么"卡片** |
| DoD | 本周课表与官方一致；能横滑切周；能切学期；"现在在干什么"在上下课边界正确切换 |
| 风险 | 中。网格 UI 要手写；学期边界/调休/单双周的处理容易出错 |

> 💡 **小组件先不做**——等功能稳定后再做，避免边改边返工。

---

### P3 · 专注（番茄钟 + 热力图）+ 桌面小组件（2–3 天）

| 项 | 内容 |
|---|---|
| 目标 | **纯本地、零接口依赖，快速做出"每天都会打开"的功能**（抗烂尾第二道保险） |
| 产出 | ① 番茄钟大圆环（`Canvas` + `drawArc`）<br>② **前台服务 + 常驻通知**，计时用 `SystemClock.elapsedRealtime()`<br>③ 标签（课表课程名自动候选 + 自定义）<br>④ 学习记录落 Room（UUID 主键 + `updatedAt`）<br>⑤ **热力图**（`LazyVerticalGrid` 7 列 × N 周，**区分"无记录"与"零时长"**）<br>⑥ **桌面小组件**：今日课表 + 番茄钟一键开始（Glance） |
| DoD | **计时跨 Doze 仍准确**（锁屏 90 分钟后核对）；热力图灰色斜纹表示无记录；小组件能刷新 |
| 风险 | 低。唯一坑是 Doze 与国产 ROM 杀后台（需引导加白名单） |

**P3 完成后你手上已是一个"每天都想用"的 App**——这是整个计划里最重要的里程碑。

---

### P4 · 一卡通完整（2–3 天）

| 项 | 内容 |
|---|---|
| 目标 | 把 P1 的电费做完整，并补上余额与消费 |
| 产出 | ① **房间选择器**（复用第三方静态数据：校区→楼栋→房间，**一次拿到照明+空调两个房间号**）<br>② **照明电费 + 空调电费**（同一接口换 `room`，`utilityType` 恒为 `electric`）<br>③ **校园卡余额**<br>④ **消费记录列表**（按日分组 + 月度合计；接口路径待定位，先 Mock）<br>⑤ **日/月用电统计** + 预估可用天数<br>⑥ **低电量提醒**（阈值默认 10 度，去重） |
| DoD | 两个房间号各查各的；日用量正确（**负值正常显示**；当天"末条>首条"识别为**充值日**不误判为负消耗） |
| 风险 | 低。唯一待办是定位消费记录的具体路径（一卡通前端可读，用 CDP 流程即可） |

---

### P5 · 空教室（2–3 天）

| 项 | 内容 |
|---|---|
| 目标 | 占用表 → **本地反算空闲** |
| 产出 | ① 校区 / 楼栋 / 楼层 / 教室类型筛选<br>② `POST /room/place/rooms` 拉指定日期的教室+占用明细<br>③ **本地反算**：全部教室 − 该时段被占用的教室<br>④ 缓存 10–30 分钟 |
| DoD | **抽样与官方 App 结果一致**；周末/假期返回空时显示"该日无占用记录"而不是"查询失败" |
| 风险 | 中。反算逻辑 + 数据量；注意 `virtual:true` 要排除，`enabled`/`seatsForLesson`/`floor` 不可靠 |

---

### P6 · 图书馆（2–4 天）

| 项 | 内容 |
|---|---|
| 目标 | 只读为主，**不碰自动预约** |
| 产出 | ① 区域 → 座位图（`/v4/Space/map`、`/v4/Space/seat`）<br>② **预约记录**（`/v4/member/seat`：地点/座位/日期/起止时间/状态）<br>③ **违规提醒**（未签到/未签离，累计 3 次停用 7 天）<br>④ 一键取消预约（`/v4/space/cancel`） |
| DoD | **校外也能用**（走 HTTP:80）；记录字段完整；被 `未签到` 的记录在统计里被过滤 |
| 风险 | 中。① 校外只有 HTTP 明文，token 明文传输（首次登录已按"只存 token"设计，暴露面有限）<br>② 图书馆 token 生命周期未知，需实测<br>③ **不做自动化预约**——签到靠闸机，违约惩罚落在用户头上 |

---

### P7 · 汇总统计 + 备份 + 打磨（3–5 天）

| 项 | 内容 |
|---|---|
| 目标 | 榨出已有数据的价值 + 让数据可持续 |
| 产出 | ① **周/月/年总结**（总时长、标签分布、图书馆行程）<br>② **图书馆时间统计**（F34，过滤 `未签到`，与番茄钟分开显示）<br>③ 校园卡消费统计<br>④ **数据备份与恢复**（JSON 导出/导入，SAF，`schemaVersion` + `updatedAt` + UUID 主键）<br>⑤ **iCal 课表导出**<br>⑥ 小组件打磨、登录诊断页完善、空状态/骨架屏 |
| DoD | 总结数字与明细能对上；**备份能在清空数据后完整恢复** |
| 风险 | 低 |

---

### P∞ · 维护（持续）

| 项 | 内容 |
|---|---|
| 每周固定一次 | 检查各功能是否仍正常（学校可能随时改版） |
| 发现异常 | 走 1.4 的应急流程（目标 < 1 小时） |
| 长期 | 远端配置热修优先于发版；只有结构性变化才发新版 |

## 三、风险登记册

| 风险 | 影响 | 缓解措施 | 首次应对阶段 |
|---|---|---|---|
| **令牌过期导致静默失败** | 高 | 登录诊断页 + 数据新鲜度 UI + 401 单飞刷新 + 打开即刷新 | P1 |
| **学校接口改版** | 高 | fixture 快照测试 + 宽松解析 + 远端配置 + 1 小时应急流程 | P1 |
| **项目烂尾** | 高 | 每阶段产出可日常使用的 APK + 优先做纯本地功能 + 强制自用一周 | P1/P3 |
| 账密登录踢掉官方 App | 中 | 只在首次/令牌彻底失效时登录；之后只复用 token；登录页明确告知 | P1 |
| 国产 ROM 杀后台 | 中 | 引导电池优化白名单 + 前台服务 + AlarmManager（不依赖 WorkManager 准时） | P1/P3 |
| 7×10 课表网格 UI 难写 | 中 | 先做纯文本格子的最简版，再迭代美化 | P2 |
| 番茄钟被 Doze 冻结 | 中 | `elapsedRealtime()` + 锚点推算 + 前台服务 | P3 |
| 图书馆仅 HTTP 明文 | 中 | 只存 token 不存密码 + 减少明文传输次数 + 首次登录提示 | P6 |
| 空闲反算结果与官方不一致 | 中 | 抽样对比 + 排除 `virtual` + 不确定性字段不用 | P5 |
| 第三方房间数据过期 | 低 | 做成可远端更新 + 抽样校验 | P4 |

## 四、工具与命令速查

```bash
# 构建 Debug
./gradlew assembleDebug
# 直接装到手机（已连接 adb）
./gradlew installDebug
# 或
adb install -r app/build/outputs/apk/debug/app-debug.apk

# 看日志
adb logcat -s ZZUPocket:D

# 重新打开 WebView 调试通道（查新接口时用）
adb forward tcp:9333 localabstract:webview_devtools_remote_<pid>
# 然后跑 _research/cdp_*.mjs
```

**工程参数**

| 项 | 值 |
|---|---|
| 显示名 | **ZZUPocket** |
| applicationId | `io.github.<你的GitHubID>.zzupocket` |
| minSdk / targetSdk / compileSdk | 26 / 36 / 36 |
| CAS deviceId | **包名**（不要用 zzupy 的 `"ZZU.Py"`） |
| 默认校区 | 主校区（`campusAssoc=2`），代码里做成 enum |
